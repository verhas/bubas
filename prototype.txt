  1. Blockers — the doc says two contradictory things

  1.1 Placeholder syntax has two incompatible orderings.

  The "Variable Placeholders" section defines name before postfix:
  {var:name:declared}   {new:var:name:initialized}
  {declared:var:name:initialized}
  The "Pattern Syntax" grammar and its examples define postfix before name:
  placeholder : ... | {prefix:var:postfix} | {prefix:var:postfix:name}
  DECLARE {new:var:declared:varName} {type:varType}
  And the "Built-In Patterns" block right below goes back to the first order:
  DECLARE {new:var:varName:initialized} {type:varType} =
  {expression:initializer}
  These cannot both be true. Worse, the grammar's own example DECLARE 
  {new:var:declared:initialized} is unparseable under either rule — both
  trailing tokens are state keywords, so there's no name at all. The rule
  "prefix and postfix names are not allowed as variable names in patterns" is
  clearly the intended disambiguator, but it only works if exactly one ordering
  is normative.

  1.2 Is a statement handler a runtime executor or a compile-time macro? Four
  mutually inconsistent descriptions:

  ┌─────────────┬─────────────────────────────────────────────┬────────────┐
  │    Where    │                  Signature                  │ Semantics  │
  ├─────────────┼─────────────────────────────────────────────┼────────────┤
  │ Custom      │                                             │ executes   │
  │ Pattern     │ .as(ctx -> { ... ctx.error(...) })          │ at runtime │
  │ Definition  │                                             │            │
  ├─────────────┼─────────────────────────────────────────────┼────────────┤
  │ API         │                                             │ returns    │
  │ Reference   │ .as(ctx -> { return new ASTNode(...); })    │ AST (and   │
  │             │                                             │ typo czx)  │
  ├─────────────┼─────────────────────────────────────────────┼────────────┤
  │             │                                             │ different  │
  │ API method  │ StatementBuilder.handler(StatementHandler)  │ method     │
  │ list        │                                             │ name       │
  │             │                                             │ entirely   │
  ├─────────────┼─────────────────────────────────────────────┼────────────┤
  │             │ .handler((ctx, parser, placeholders) -> new │ 3-arg      │
  │ Example 3   │  AssignmentNode(...))                       │ macro      │
  │             │                                             │ expansion  │
  └─────────────┴─────────────────────────────────────────────┴────────────┘

  This is the single most consequential undecided thing, because it determines
  whether Phase 3 (code generation to Java) is even possible. If handlers are
  runtime lambdas, custom statements cannot be compiled to standalone Java — the
  generated program would have to call back into the interpreter's registry,
  which contradicts "Generated Java compiles and runs" as a standalone
  deliverable. The doc never addresses this.

  1.3 Three different array declaration syntaxes.
  - Composite Types table: ARRAY INTEGER[10]
  - Built-in pattern: DECLARE {new:var...}[{integer:size}] {type:varType}
  - Example 2: DECLARE numbers[5] INTEGER

  The table contradicts the other two (which agree with each other).

  1.4 Constraints and state cannot be combined, but the examples combine them.
  The grammar lists {type/constraint:name} and {prefix:var:postfix:name} as
  disjoint alternatives. Yet the VALIDATE example writes {var/STRING:item} and
  {initialized:expression/STRING:rules}. The second is doubly broken:
  initialized is a variable state applied to an expression placeholder, which
  has no declaration state.

  This also creates a real expressiveness gap: there is no way to write "must be
  a declared INTEGER variable, will be initialized after" — you'd need
  {declared:var/INTEGER:x:initialized}, which no grammar in the doc admits.
  Compounded by the rule "when a placeholder defines a required type it implies
  the variable is initialized," which makes typed output parameters impossible.

  1.5 VOID is and is not a keyword. It's in the keyword list; "Special Types"
  says "these are not keywords as they are not used in BUBAS code."

  2. Unspecified language semantics (needed before the lexer/parser)

  Statement/expression grammar:
  - Function calls have two syntaxes — expression form LOAD_ORDER(123) and bare
    statement form PROCESS_ORDER order, LOG_EVENT "INFO", msg. The bare form
    appears in three examples and is never defined anywhere in the language
    spec. It also collides head-on with pattern matching: how does the parser
    tell PROCESS_ORDER order from a custom pattern? Which wins?
  - Post-test loops exist but have no syntax. The definite-assignment section
    says "loop body with WHILE or UNTIL at the end of the loop is guaranteed to
    execute," and DoWhileNode has isWhile — but there is no field distinguishing
    pre- from post-test, and no example, no closing keyword (LOOP? END DO?).
  - ; as a separator appears only in Phase 1's success criteria (DECLARE x 
    INTEGER; LET x = 42). Nowhere in the spec.
  - RETURN in a language with no functions — returns what, to whom?
    ReturnNode.value is optional. interpreter.execute() returns nothing in the
    example. Is there a program result value at all?
  - END is overloaded: block terminator (END IF/END FOR/END PROGRAM) and a
    program-terminating statement. Grammar never disambiguates.
  - Continuation character: text says "ends with a backslash (_)". Backslash is
    \, underscore is _. Which?
  - Can custom patterns start with IF/FOR/DO/ELSE/THEN? Only PROGRAM, RETURN,
    END are forbidden.
  - Pattern matching algorithm is entirely undefined: ordering, ambiguity
    resolution, longest match, backtracking. Critical case: {expression} is
    greedy and multi-token — how does the matcher know where the expression ends
    in ADD {number:amount} TO {var:total} if an expression could itself contain
    TO?

  Values and arithmetic:
  - NULL is used as the OPAQUE default but is not a literal, not a keyword, and
    there's no way to test for it. (Argument.isNull() means something unrelated
    — see 3.4.)
  - INTEGER division: "floor" — floor or truncation? They differ for negatives.
    MOD sign for negatives? Division by zero?
  - DECIMAL division on BigDecimal: no MathContext, scale, or rounding mode. 1/3
    throws ArithmeticException as written.
  - INTEGER overflow (Long): wrap or error?
  - = on DECIMAL: equals (2.0 ≠ 2.00) or compareTo? On OPAQUE: identity or
    .equals? On STRING: is < legal?
  - Anything→STRING coercion: is 42 + "x" legal or only "x" + 42? How do
    BOOLEAN, DECIMAL, OPAQUE render?
  - FOR loop: is the bound re-evaluated each iteration? Negative STEP? Is the
    loop var declared by the loop or pre-existing (Example 2 pre-declares it)?
    Writable in the body? INTEGER only?
  - Array index out of bounds; index is Long but ArrayValue.get(int); no LENGTH
    function; sizes must be integer literals, so no computed sizes.
  - Arrays can't cross the Java boundary. BasicType has no array variants,
    function parameters are scalars only, and "expressions cannot have ARRAY
    type." So arrays are reachable only via patterns. Intended, but unstated.
  - No standard library is specified, yet TO_INTEGER/TO_DECIMAL are cited as the
    official coercion mechanism, and PRINT_RESULT/REPORT_TOTAL appear in
    examples undefined.
  - Identifier collision rule ("can't have apple and Apple") is really
    "identifiers must be unique case-insensitively" — say that. Are function
    names case-sensitive? Can functions be overloaded by arity?

  3. Model-level contradictions

  3.1 Context.setVariable(name, value) destroys every static guarantee. The
  whole value proposition is compile-time typing, finality, and definite
  assignment — and the Context interface hands Java functions unrestricted keyed
  write access to globals. A function can overwrite a FINAL, change a
  variable's type, or satisfy nothing the analyzer assumed. Either restrict it,
  or drop the guarantee claims.

  3.2 Context is "ephemeral" but holds the service registry. The glossary and
  Java Integration section both call Context an ephemeral per-call object;
  Example 4 calls interpreter.getContext().registerService(...), treating it as
  long-lived config. registerService is not in the Context interface either, and
  getContext() is in no API listing.

  3.3 VariableState conflates two orthogonal axes. Variable has both state ∈ 
  {UNDECLARED, DECLARED, INITIALIZED, FINAL} and a separate isFinal boolean.
  Since "final postfix implies new prefix," a FINAL variable is always also
  initialized — so FINAL cannot be a peer of INITIALIZED in one enum. It should
  be (declaredness × mutability).

  3.4 Optional placeholders are used but never defined. Argument.isNull() is
  documented as "placeholder is optional in the pattern and was not defined" —
  the pattern grammar has no optionality marker at all.

  3.5 The two LET built-in patterns overlap ambiguously. LET {initialized:var:x}
  = ... and LET {declared:var:x:initialized} = ... — an already-initialized
  variable matches both. Also, why would plain assignment require the target to
  be already initialized? The earlier Compile-Time Validation example annotates
  LET x = 10 as {declared:var:x:initialized} only, contradicting the built-in
  list.

  3.6 ctx.error() is documented under "Logging" but specified to throw 
  BasicException. Pick one.

  3.7 Nothing states whether an interpreter/script is thread-safe or reentrant.
  With a single global symbol table, presumably not — but this matters for an
  orchestration engine and should be explicit. Same for the required order of
  defineFunction/defineStatement calls relative to compilation.

❯ A non-final variable can be set via setVariable. There is no any other way to 
  change the value of a non-final variable. Also there is no other way to       
  declare and initialize a variable. The command LET and command DECLARE are    
  defined using patterns and the executions of these commands will call come    
  function that gets the context and modifies the variables. It is a real       
  concern that the context passed to a function should NOT allow the change of  
  a variable, so it may be a context that may not contain this callback.        

⏺ That's a clean model — it makes DECLARE and LET genuinely non-special: they're
  registered patterns like any other, and the only privileged operation in the
  whole language is "a statement handler mutates the variable store." Everything
  else is expression evaluation. That collapses a lot of the spec's redundancy.

  It does put a direct tension on the macro answer, though, and I want to pin
  that down before anything else.

  The tension: if LET is a pattern whose execution calls a handler that receives
  a context and calls setVariable, that's a runtime executor, not a
  compile-time macro. A pure macro would expand LET x = 5 into an AssignmentNode
  at compile time and never call user code at runtime — and then setVariable is
  an interpreter-internal API that no handler ever sees. Both are coherent
  designs; the doc currently mixes them, and your two answers land on opposite
  sides.

  Two other consequences worth flagging now:

  Finality can't go through setVariable. You said a non-final variable is set
  via setVariable, and there's no other way to declare/initialize. But DECLARE y
  INTEGER FINAL = 20 has to create something immutable, which setVariable by
  definition can't do. So the statement context needs at least two operations —
  a declare(name, type, value, isFinal) and a set(name, value) — with set
  rejecting finals at runtime. Similarly LET a[i] = v can't be expressed as
  setVariable(name, value); it needs either an element-write operation or
  mutable ArrayValue handles.

  Postconditions become a trust boundary. The definite-assignment analyzer
  believes a pattern's :initialized postfix. Nothing currently forces the
  handler to actually have written the variable — a handler that promises
  :initialized and takes an early exit leaves the analyzer's model wrong, and
  every downstream read is unsound.

⏺ Two notes before the new requirement.

  Your postcondition answer effectively settles the execution model. "Verify at
  handler return" only has meaning if a handler runs at runtime. Under a pure
  macro model there is no handler and no return — the expansion is checked
  structurally at compile time and there's nothing to verify. So pure macro is
  out; it's hybrid or pure executor.

  Read-only getVariable has one wrinkle to decide: what it returns for a
  variable that is DECLARED but not INITIALIZED. It's the one hole read-only
  access can't close, because a by-name read is invisible to the
  definite-assignment analyzer — the function reads x, the analyzer never sees a
  use, and x may legitimately have no value yet. Cleanest answer is that it
  throws rather than returning the type's default, so it fails at the read
  instead of silently propagating a zero.

  The missing syntax: type references between placeholders

  You're right, and it's a bigger hole than it first looks — it affects the
  built-ins, not just custom patterns. DECLARE x INTEGER = 5 needs "the
  initializer's type must match {type:varType}", and LET x = expr needs "the
  expression's type must match the declared type of the variable bound to 
  another placeholder". Those are two different references, and neither is
  expressible today.

  Here's the smallest extension I can find that covers both. Widen constraint so
  it accepts a reference to another placeholder in the same pattern, alongside
  the existing type keywords:

  constraint       : type_constraint | array_constraint | type_reference
  type_constraint  : INTEGER | DECIMAL | STRING | BOOLEAN | OPAQUE | NUMBER
  array_constraint : ARRAY [ / type_constraint ]
  type_reference   : placeholder_name [ "[]" ]

  /T resolves by what T denotes:

  ┌───────────────────────────────┬─────────────────────────────────────────┐
  │             T is…             │                /T means                 │
  ├───────────────────────────────┼─────────────────────────────────────────┤
  │ a {type:T} placeholder        │ the type keyword actually written at    │
  │                               │ that position                           │
  ├───────────────────────────────┼─────────────────────────────────────────┤
  │ a {var:…:T} placeholder       │ that variable's declared type           │
  ├───────────────────────────────┼─────────────────────────────────────────┤
  │ an {expression:T} placeholder │ that expression's static type           │
  ├───────────────────────────────┼─────────────────────────────────────────┤
  │ any array-typed placeholder,  │ its element type                        │
  │ as /T[]                       │                                         │
  └───────────────────────────────┴─────────────────────────────────────────┘

  Names are resolved against the pattern; an unknown name is a
  pattern-definition error, not a silently-free variable.

  That makes every built-in expressible for the first time:

  DECLARE {new:var:declared:name} {type:T}
  DECLARE {new:var:initialized:name} {type:T} = {expression/T:init}
  DECLARE {new:var:final:name} {type:T} FINAL = {expression/T:init}
  DECLARE {new:var:initialized:name}[{integer:size}] {type:T}

  LET {declared:var:initialized:name} = {expression/name:value}
  LET {initialized:var/ARRAY:arr}[{expression/INTEGER:index}] =
  {expression/arr[]:value}

  And it gives custom patterns same-type constraints for free, with no extra
  machinery — SWAP {var:a} WITH {var/a:b} requires b to have a's type.

  One semantic decision this forces: DECLARE d DECIMAL = 5 must be legal, since
  INTEGER→DECIMAL widening is automatic. So /T has to mean assignment-compatible
  with T, not identical to T. That's probably what you want everywhere, but it
  means a pattern author cannot demand exact type identity unless we also give
  them a spelling for it.

⏺ Both clarifications tighten things usefully.

  Whole-line matching removes most ambiguity but not all. DECLARE x INTEGER and
  DECLARE x INTEGER = 5 are indeed different line shapes, so no conflict — good.
  But overlap survives wherever two placeholder kinds accept the same token
  sequence, since a bare variable is also a valid expression:

  SET {var:target} TO {expression:value}
  SET {var:target} TO {var:source}      ' 'SET x TO y' matches both

  So the "more than one match is an error" rule still has real work to do. And
  to answer your open question: yes, it's detectable statically, if you accept a
  conservative approximation. Each pattern is a sequence of literal keywords
  and holes over token classes; approximate {expression} as "one or more
  non-reserved tokens" and every pattern becomes a regular language over token
  classes. Pairwise intersection-emptiness on regular languages is decidable and
  cheap. It's conservative — it can flag a pair that never actually collides on
  real input — so the question is whether you want that false-positive risk at
  registration or the conflict surfacing later at parse.

  The startup reservation rule implies a sealing phase. If pattern keywords
  become reserved before any source is analysed, then registration must close
  before the first compile — otherwise a later defineStatement could reserve a
  word that an already-compiled program used as an identifier. Worth making
  explicit in the API: defineFunction / defineStatement throw once the first
  source has been parsed, and the function-name/pattern-keyword collision check
  runs at seal.

  One item I'll assume unless you object: patterns match the logical line —
  after continuation joining and trailing-comment stripping — not the physical
  line.

  Three consequences of the runtime-mutable MathContext, none fatal but all
  needing a line in the spec:

  Constant folding on DECIMAL division becomes unsound. LET x = 1.0 / 3.0 cannot
  be folded at compile time, because the MathContext in force when that line
  executes isn't statically known. Constant folding stays available for +, -, *
  and all INTEGER arithmetic; division is excluded.

  Generated Java must read the context from the runtime, not bake a literal in —
  so DECIMAL division joins custom statements on the list of things that keep
  the runtime on the classpath.

  Reproducibility is now a runtime property. The same source can yield different
  results across runs depending on whether the context-setting function ran.
  Worth stating outright so nobody treats it as a bug.

  Two follow-ons I'll assume unless you object: the default is
  MathContext.DECIMAL128 with HALF_EVEN, and the context applies to division
  only — +, -, * stay exact, since rounding them would silently truncate money
  arithmetic that BigDecimal handles correctly. Also, "one program at a time"
  should be stated as: an Interpreter instance is not thread-safe and a run is
  exclusive; concurrent orchestration means one interpreter per thread.

⏺ Two design questions asked of me — here's my take on each.

  Separators. I'd reject "any non-alphanumeric" outright: it guarantees five
  spellings of the same pattern inside one codebase, breaks grep and diff, and
  denies an LLM a canonical form to imitate. A grammar should have exactly one
  spelling.

  Spaces-only reads nicely but leaves the zones invisible — the reader still
  finds the pivot by knowing which words are slot kinds — and it overloads the
  very character that separates literal keywords in the surrounding pattern
  text. All-colon is unambiguous, as you say, but has the same invisible-pivot
  problem.

  The real issue is that initialized means one thing before the slot and another
  after it, so position carries meaning that nothing marks. There are two
  honest fixes: mark the zones (>) or stop reusing the vocabulary (is_ /
  becomes_). Your is_ instinct is right about the underlying problem, but
  is_initialized alone doesn't solve it — a postcondition would need
  becomes_initialized, or order still matters.

  My recommendation is >, with spaces optional and ignored inside the braces.
  Pattern authors are few, they re-read their own patterns, and terseness inside
  a Java string literal is worth real money. pre > kind:name > post reads
  directionally, and the arrow is exactly where the meaning flips.

  Services. Your reading is correct — BUBAS has no syntax for services and
  cannot observe them; they exist purely for Java-side function and handler
  implementations.

  On the $my_service idea, I'd advise against it. It contradicts the decision
  that only statement handlers may write variables while functions get read-only
  access; it puts run-scoped infrastructure into the same namespace the
  definite-assignment analyser reasons about, requiring a carve-out for $ names;
  and a Class-keyed lookup gives better errors than a stringly-typed hidden
  slot. Services should stay a separate, explicit mechanism.

  Language-level registration is right for singletons, and the qualifier need is
  real — (Class, String) with an empty default is the familiar shape.

⏺ Two corrections taken.

  You're right that my second option was incoherent — a pattern's leading word
  becomes reserved by definition, so "must not be a reserved word" is vacuous.
  The real rule is narrower: no pattern may start with a structural keyword
  (PROGRAM, IF, ELSEIF, ELSE, DO, WHILE, UNTIL, FOR, EXIT, RETURN, END), because

  existing pattern keyword like DECLARE stays legal if overlap analysis passes,
  so an embedder can add a declaration variant but never displace a built-in.
  And the guidance goes in the spec as guidance: pick WHEN, not IF.

  The case rule is now three-way and consistent: keywords — core and registered
  command words alike — are fully case-insensitive; names — variables, function
  names, opaque types — are unique case-insensitively but must be written
  exactly as registered or declared. One signature per function name; no
  overloading.

  literal is not a continuation, a trailing comment may appear on an
  intermediate physical line and is stripped before joining, and every "line"

  parser finds the zone naming a kind and takes what's before as preconditions,
  after as postconditions — no positional rule to remember or get backwards.

⏺ Overlap analysis done — 136 tests green (46 lexer, 90 analyser).

  Three classes in bubas-analyser:

  - TokenClass — what a pattern element can consume at one position, abstracted
    from real tokens: Exact(type, text) plus NAME, TYPE_NAME, CONSTANT, SIGN,
    EXPRESSION.
  - PatternAutomaton — a pattern as an NFA over those classes. A var is a name
    with an optional bracketed index, a literal is an optional sign then a
    constant, an expression is one-or-more expression tokens.
  - OverlapAnalysis — instantiated with the sealed Vocabulary, check(patterns)
    at seal. A pair overlaps when the product of their automata reaches a state
    where both accept.

  The compatibility table is where the real content is. Most patterns that look
  distinct aren't, because a name is an expression and so is a constant — which
  is exactly why SET {var} TO {expression} and SET {var} TO {var} collide.
  Meanwhile NAME, TYPE_NAME, CONSTANT and SIGN are pairwise disjoint: names are
  unreserved words, type names are reserved, constants are literals or
  TRUE/FALSE, signs are operators.

  The test that justifies the seal-time placement: PAY {expression:a} VIA 
  {var:b} and PAY {expression:a} FROM {var:b} do not collide — but only because
  VIA and FROM are reserved by those very patterns, so neither expression can
  swallow the other's keyword. Run the same check before registration finished
  and it would report a false conflict. The test says so in a comment, and
  SPEC.md §9.1 now states it as the reason the check can't run earlier.

  All five built-ins are verified conflict-free, and still are with VALIDATE and
  PAY added.

  Two deliberate choices worth knowing:

  Every colliding pair is reported at once rather than failing on the first,
  matching how compilation errors are meant to behave — an embedder sees all
  conflicts in one go.

  The approximation errs towards warning: expressions carry no bracket structure
  in the automaton, so it accepts sequences the matcher would reject. A pair
  may be reported that no real line could hit; no colliding pair can slip
  through. That's the safe direction, and it's why skipOverlapAnalysis(true)
  exists — but it's a reason the flag exists, not a reason to use it.

⏺ Now the invariance question. Here's the whole issue.

  Where it can possibly matter is narrower than it looks. Arrays are never
  assigned in BUBAS — x = numbers is an error, arrays aren't expressions — and
  can't be returned. So array assignability is consulted in exactly one place:
  matching an array argument against a function parameter. Nowhere else.

  The concrete case. RushOrder extends Order in Java, both registered as opaque
  types:

  DECLARE rushes[10] RushOrder
  SORT_ORDERS(rushes)
  public void sortOrders(Context ctx, Order[] orders) { ... }

  Under covariance this call type-checks. And §10.2 hands the handler the 
  interpreter's actual backing store, not a copy — that's what makes
  SORT_ITEMS(items) reorder the script's array. So the handler holds a real
  RushOrder[] typed as Order[], and:

  orders[0] = new Order();   // compiles; throws ArrayStoreException

  Java catches it, but as a Java exception inside embedder code, at runtime,
  with nothing pointing at the BUBAS line that passed the array. Under
  invariance the call is simply rejected at compile time, with a diagnostic
  naming both types.

  Scalars are unaffected either way — long[] and BigDecimal[] were never
  related. The whole question is opaque element types with a real hierarchy.

  The honest cost of invariance: a purely reading function is blocked too.
  SUM_TOTALS(Order[] orders) can't take RushOrder[], even though reading is
  safe. The existing escape hatch is ANY_ARRAY, but that's a poor substitute —
  the handler gets BubasArray.raw() as Object and has to cast, losing exactly
  the typing that made native arrays worth having.

  I also considered handing over a defensive copy under covariance, which would
  make writes sound. It's out: copying breaks in-place reorder, which is a
  settled behaviour with SORT_ITEMS(items) as its stated example.

⏺ That changes my recommendation, and it's worth saying so plainly: I was
  optimising for the wrong thing. Performance was never the interesting axis —
  divergence between backends is, and that argues against the plain tree-walker
  I proposed.

  Here's the specific mechanism. The checked AST holds language-level nodes:
  Binary("+") with two operand subtrees. Every backend then has to independently
  work out what that + means — string concatenation or arithmetic, whether an
  INTEGER needs widening, whether the overflow check applies, whether DECIMAL
  division reads the MathContext. Three backends deciding that separately is
  three chances to decide differently, and the differences are exactly the
  subtle kind that a debugged script would hit in production.

  The fix is to make those decisions once, in a lowering step, and hand every
  backend an unambiguous operation:

  Binary("+", INTEGER, DECIMAL)   →   AddDecimal(WidenToDecimal(l), r)
  Binary("+", STRING, INTEGER)    →   Concat(l, TextOf(r, INTEGER))
  Binary("+", INTEGER, INTEGER)   →   AddIntegerChecked(l, r)
  Binary("=", DECIMAL, DECIMAL)   →   CompareDecimalByValue(l, r)

  After that the interpreter isn't implementing "the language", it's
  implementing a list of named operations — and so is the Java emitter, and so
  would a Rust one. A conformance failure becomes a backend bug rather than two
  readings of the specification.

  It should be a lowered tree, not flat bytecode. Keeping If/Loop/For structure
  means the Java generator emits natural Java rather than reconstructing control
  flow from jumps, source positions survive for diagnostics, and the debugging
  seam sits on the same statement boundaries in every backend — which is what
  makes stepping behave the same compiled as interpreted.

  One limit worth naming now, because it bounds the Rust idea: BUBAS functions
  and commands are Java classes. A Rust backend could share the core semantics
  but could not call the vocabulary — every function would need a Rust
  implementation. So the equivalence guarantee is available for what BUBAS pins,
  and stops at the boundary where the embedder's code begins.

  What the core IR pins

  Four types in javax0.bubas.analyser.core. The value is in what each node makes
  impossible to re-decide:

  - Widen and Text are nodes, not implicit conversions, so no back end infers
    them.
  - Arithmetic(kind, operator, …) separates INTEGER from DECIMAL at the node, so
    integer overflow trapping and decimal MathContext reading can't be confused
    for one another. MODULO exists only for INTEGER.
  - Compare(kind, relation, …) carries what's being compared, so decimals
    compare by value and never by scale.
  - Logical is documented as short-circuiting, pinning evaluation order rather
    than leaving it to each back end.
  - Loop absorbs UNTIL as a negated WHILE, and Break names its loop by identity
    rather than by kind — so no back end re-derives which loop EXIT FOR leaves.
  - Slot everywhere; no variable name survives into execution.

  CoreProgram.slots is a flat array with parameters first, which your
  top-level-declaration rule is what makes possible — the variable set is fixed
  before the program starts, so there are no frames and no scopes.

  CoreStatement.Assign, AssignElement and Allocate are gone with it. They
  described a lowering that shouldn't happen — every statement pattern is an

  code generator does with a command is a question for the command's own
  semantic description rather than for the core tree.

  bubas-support exists, depending only on bubas-api — which is the point of
  having split the API out. It holds five ordinary implementations:

  - Declare — an empty body, and correctly so: the placeholder carries a type
    constraint, so the runtime already made the slot, and a declared
    postcondition has no value to supply.
  - DeclareInitialized, DeclareFinal — one set each; finality is settled by the
    pattern.
  - DeclareArray — the only one with real work: a native Java array of the
    element type, with STRING and DECIMAL filled to their defaults since Java's
    zero-fill doesn't reach them. Opaque arrays stay null-filled, because null
    is an ordinary value for one and the language has no way to make anything
    else.
  - Assign — evaluates the index first when the reference is indexed, then
    writes. That's the at-most-once contract being honoured by its first real
    caller.

  The four test languages now install these through Standard.STATEMENTS rather
  than defining their own stubs, so the shipped implementations are exercised by
  every downstream test.

  Two things to flag

  SPEC.md still records the reversed decision — §3, §9.6 and §13 all say
  built-ins expand to core AST nodes while custom patterns call handlers. That
  needs rewriting to match, along with §13's compilation story, which should
  become "a command may supply a target-independent semantic description;

  And a smaller one: Standard.STATEMENTS used Map.copyOf, which doesn't preserve

  - mixed arithmetic widens both sides to the same type before the operation
  - decimal comparison is Compare(DECIMAL, …), never a scale-sensitive equality

  to. Now only Type, Reference and Element constraints drive coercion — the same

  operations, which is now a much smaller job than it would have been over the
  AST, because every decision it would have had to make has already been made.
